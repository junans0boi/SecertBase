# 01. Grilling — 블랙잭·도둑잡기·제로·해적 룰렛·패널티킥 2.0

> 2026-11-05. 지난 정비(`game-overhaul-2026-11`)와 같은 **셀프 그릴링**입니다. 질문(❓)마다 추천 답(➡️)을 적고 곧바로 **결정**으로 확정했습니다.
> 근거: `00-analysis.md`(코드·실제 플레이·시뮬레이션), `CONTEXT.md`의 **놀이(Play)** 정의("승패보다 같은 시간에 함께 행동하는 경험 우선"), ADR-0001(원카드 내부 식별자 `uno` 유지).
> **사용자가 승인 때 뒤집을 수 있는 결정**은 맨 끝 "승인 시 확인할 결정"에 모았습니다.

---

## Round 1 — 목적지와 범위

❓ **Q1 - 이번 작업의 목적지는?**

➡️ 결정: 5종을 **탱크 대작전 2.0에 준하는 수준으로 새로 만듭니다.** 규칙, 화면, 연출, 소리를 함께 올립니다. 다만 모든 게임의 규칙을 바꾸지는 않습니다. 시뮬레이션에서 **규칙이 사실상 틀린 것으로 나온 3종**(블랙잭, 제로, 패널티킥)만 규칙을 바꾸고, 도둑잡기·해적 룰렛은 규칙을 유지한 채 공정성만 보정합니다.

❓ **Q2 - 5종 말고 다른 게임은?**

➡️ 결정: 건드리지 않습니다. 공통 장치(카드 그림, 효과음, 재시작 동의)는 다른 게임이 나중에 쓸 수 있게 **공용 모듈**로 만들되, 이번에는 5종과 탱크의 효과음 이전만 적용합니다.

❓ **Q3 - 시작 전 선행 조건은?**

➡️ 결정:
1. **PR #216(탱크 UI 개편)을 먼저 머지**합니다. 효과음 합성기를 공용으로 옮기는 작업(F02)이 `tank/` 파일을 건드리기 때문입니다.
2. 사용자가 점심에 해 보는 탱크 테스트에서 나온 문제를 먼저 처리합니다.
3. 이 계획이 승인되기 전에는 코드를 바꾸지 않습니다.

❓ **Q4 - 새 의존성(오디오 파일, 이미지 에셋, 패키지)을 추가할까요?**

➡️ 결정: **추가하지 않습니다.** 효과음은 탱크처럼 코드로 합성하고, 그림은 `CustomPainter`로 그립니다. 저작권 걱정이 없고, 파일 크기와 로딩이 늘지 않으며, 테스트에서 파형을 검증할 수 있습니다.

## Round 2 — 공통 장치

❓ **Q5 - 카드는 글자로 그릴까요, 그림으로 그릴까요?** (C1)

➡️ 결정: **벡터 그림**입니다. 무늬 4종은 `Path`로, 뒷면은 패턴 `CustomPainter`로, 숫자·문자는 앱 글꼴로 그립니다. 공용 위젯 `PlayingCard`(앞면/뒷면/조커/크기 변형)를 만들어 블랙잭과 도둑잡기가 같이 씁니다. `🂠`, `♠♥♦♣` 글자는 더 이상 쓰지 않습니다. 글꼴 로딩과 무관하게 항상 같은 모양이 나옵니다.

❓ **Q6 - 화면 톤은 어떻게 통일할까요?** (C2)

➡️ 결정: 앱의 `kMain*` 파스텔 토큰을 기본으로 하고 게임마다 포인트 색을 둡니다.
- 블랙잭: 연한 민트 펠트 테이블
- 도둑잡기: 따뜻한 허니·라일락 카드 테이블
- 제로: 하늘색 스테이지
- 해적 룰렛: 따뜻한 나무색 부두
- 패널티킥: 맑은 낮 경기장

짙은 남색 화면은 만들지 않습니다. 탱크처럼 "전투"가 주제일 때만 어두운 톤을 씁니다.

❓ **Q7 - 효과음은 어떻게 공용화할까요?** (C5)

➡️ 결정: 탱크의 `TankSynth`/`TankSfx`를 **`core/game_sfx/`로 옮겨 일반화**합니다. 합성기(웨이브·필터·노이즈 블록)는 그대로 두고 **소리 레시피만 게임별 파일**로 나눕니다. 음소거 설정은 지금 키(`tank_sfx_muted`)에서 하나의 키(`game_sfx_muted`)로 합치고, 옛 값은 한 번 읽어 옮깁니다. 웹에서만 소리를 내고 테스트에서는 아무것도 하지 않는 구조(조건부 import)도 그대로 둡니다. 진동(`HapticFeedback`)은 웹에서 동작하지 않으니 새로 쓰지 않습니다.

새 소리(각 0.1~1.5초):

| 용도 | 소리 |
|---|---|
| 카드 | 딜(슥), 뒤집기(탁), 버리기(짝), 조커(불길한 음) |
| 승부 | 버스트(둔탁), 승리, 패배, 라운드 종료 |
| 해적 | 칼 꽂기, 통 삐걱, 폭발(만화풍), 해적 날아감 |
| 축구 | 휘슬, 킥, 그물, 환호, 탄식, 선방 |
| 제로 | 카운트(똑·똑), 공개(짠), 적중 |
| 공통 | 타이머 경고, 클릭, 보상 |

❓ **Q8 - "다시 하기"를 어떻게 바꿀까요?** (C3)

➡️ 결정: 5종을 `RESTARTABLE_GAME_TYPES`에 넣고 기존 **재시작 프로토콜**(`game:restart:request/respond`, Redis 요청 레코드)을 그대로 씁니다. 결과 화면의 버튼은 "재대결 요청"이 되고, 상대가 수락하면 새 판이 같은 방에서 시작됩니다. 거절·무응답이면 요청 쪽에 안내가 뜹니다. `GameMenuButton`/`GameMenuListener`로 감싸서 메뉴에서도 요청할 수 있습니다.

❓ **Q9 - 결과 저장을 어떻게 안정화할까요?** (C3b)

➡️ 결정: 5종 모두 판마다 `gameId`를 만들고, **`recordGameOutcome({ gameId })` 하나로** 결과·XP·미션을 저장합니다. 해적 룰렛의 직접 호출과 await 없는 XP를 없앱니다. 같은 `gameId`는 한 번만 기록됩니다(이미 `game_results.game_id` UNIQUE가 있습니다).

❓ **Q10 - 재대결 사이의 전적을 보여 줄까요?** (C8)

➡️ 결정: 예. 재시작할 때 방의 **시리즈 전적**(`series`)을 유지하고 결과 화면에 "이번 방 전적 나 3 : 2 상대"를 보여 줍니다(탱크 2.0 방식). 승패가 없는 판(무승부)은 전적에 더하지 않습니다.

❓ **Q11 - 잠수 안내가 엉뚱한 화면에 뜨는 문제는?** (C6)

➡️ 결정: 서버가 이미 보내는 `gameType`을 클라이언트가 읽어, **지금 보고 있는 게임과 같을 때만** 안내를 띄웁니다. 다른 화면이면 띄우지 않습니다(서버의 기권 처리와 기록은 그대로). 안내 문구에는 게임 이름을 넣습니다("도둑잡기에서 상대가 …").

❓ **Q12 - 로비 시작과 게임 안 시작이 두 번인 문제는?** (C4)

➡️ 결정: 로비의 "게임 시작"이 곧 게임 시작입니다. 게임별로 따로 받던 설정은 다음처럼 처리합니다.
- 블랙잭·도둑잡기·패널티킥: 설정이 없으니 로비 시작 즉시 판이 열립니다.
- 제로: 설정 없음(규칙 고정).
- 해적 룰렛: 구멍 수는 **시작 전 화면에서 양쪽이 같이 보고**, 시작하는 사람이 프리셋 하나(빠른 6 / 보통 8 / 길게 12)를 고릅니다. "방장만 정한다"는 규칙을 없앱니다(Q33).

❓ **Q13 - 공용 연출 부품은?** (C7)

➡️ 결정: 탱크에서 검증한 부품을 **일반화해서 재사용**합니다.
- `GameTurnBanner`: "내 차례!" 배너
- `GameResultSheet`: 승/패/무 + 전적 + 재대결 버튼 + 색종이
- `GameToast`: 조작부를 가리지 않는 안내
- `ConfettiBurst`: 색종이

각 게임이 자기 색으로 꾸밉니다. 탱크의 같은 부품은 이번에 건드리지 않고, 공용 부품이 안정되면 나중에 옮깁니다.

## Round 3 — 블랙잭

❓ **Q14 - 승부를 어떻게 끝낼까요?** (§2 진단 1)

➡️ 결정: **먼저 2승하면 끝**, 최대 5라운드입니다. 무승부 라운드는 승수에 더하지 않고 다음 라운드로 넘어갑니다. 5라운드 뒤에도 2승이 없으면 무승부입니다.
- 시뮬레이션(스탠드 15~17, 각 2만 판): **최종 무승부 0.7~1.8%**(지금 37~40%), 평균 약 2.9라운드, 3라운드 이상 가는 판 40~43%.
- 한 판 길이는 지금(고정 2라운드)과 비슷합니다.

❓ **Q15 - 설명 문구("딜러 역할 교대")대로 딜러를 도입할까요?**

➡️ 결정: **도입하지 않고 문구를 고칩니다.** 딜러는 규칙대로 자동 진행해서 한 사람이 할 일이 없어집니다. 둘 다 능동적으로 선택하는 지금 구조가 커플 놀이에 맞습니다. 로비 설명은 "숨은 카드 한 장으로 겨루는 1:1 21점 대결"로 바꿉니다.

❓ **Q16 - 정보는 어디까지 공개할까요?** (§2 진단 3)

➡️ 결정: 처음 받은 **카드 2장 중 1장은 공개(업카드), 1장은 비공개(홀카드)** 입니다. 히트로 받는 카드는 카지노 규칙처럼 **앞면으로 공개**합니다. 나머지 정보는 이렇게 공개합니다.
- 상대의 업카드, 히트로 받은 카드, 카드 장수, **히트/스탠드/버스트 상태는 즉시 공개**.
- 상대 점수는 "공개된 카드 합 + ?"로만 표시(홀카드 값만 모릅니다).
- **블랙잭 여부는 끝까지 비공개**(공개하면 상대가 전략을 바꿀 수 있어서).
- 라운드가 끝나면 숨은 카드를 한 장씩 뒤집어 공개.

이렇게 하면 "상대는 아직 뽑는 중인가, 멈췄나", "업카드가 10이니 합이 19 정도일까"를 읽는 재미가 생깁니다.

❓ **Q17 - 버스트는?**

➡️ 결정: **버스트한 사람이 즉시 라운드를 집니다.** 상대는 더 할 일 없이 바로 공개 연출로 넘어갑니다(지금은 상대가 한 번 더 눌러야 끝나는 불필요한 단계가 있습니다).

❓ **Q18 - 누가 먼저 하고, 후공의 정보 이점은 어떻게 상쇄할까요?**

➡️ 결정: 1라운드 선공은 무작위, 이후 **직전 라운드 패배자가 후공**을 가져갑니다(후공이 상대의 최종 상태를 보고 결정하므로 유리). 무승부 라운드는 선후공을 바꿉니다. 지는 쪽이 따라잡을 장치가 생깁니다.

❓ **Q19 - 판돈은?**

➡️ 결정: 별도 선택 티켓(**B03**)으로 분리합니다. 기본은 판돈 없음이고, 켜면 `STAKE_GAME_TYPES`에 `blackjack`을 추가해 로비 준비 완료 절차와 기존 정산을 그대로 씁니다. 승인 때 **포함 여부를 정해 주세요**(끝 목록 D1).

❓ **Q20 - 시간 제한은?**

➡️ 결정: 내 결정 차례에 **30초**. 시간이 지나면 **자동 스탠드**합니다. 연속 3회면 기권입니다. 기존 AFK(60초 경고·90초 기권)는 안전망으로 남깁니다. 화면에 남은 시간 링을 보여 줍니다.

❓ **Q21 - 덱은?**

➡️ 결정: 라운드마다 새 52장을 섞습니다. 덱이 비는 일이 없어지고 `hit`의 빈 덱 분기를 없앱니다.

## Round 4 — 도둑잡기

❓ **Q22 - 뽑은 카드를 어떻게 알려 줄까요?** (O2, O4)

➡️ 결정: 뽑기 직후 서버가 **전용 이벤트 `game:oldmaid:drawn`**을 보냅니다.
- 내용: `{ by, slot, card, paired, pairedRank, jokerMoved }`.
- **뽑은 사람**은 실제 카드를 받습니다.
- **뺏긴 사람**은 자기 카드가 뺏긴 것이니 그 카드(랭크·무늬)를 받습니다(어차피 자기가 아는 정보).
- 조커 위치를 알 수 있는 값(상대 손패의 실제 id)은 보내지 않습니다.

화면 연출은 이렇습니다.
- 뽑은 쪽: 상대 카드가 중앙으로 날아와 **크게 뒤집힌 뒤** 내 손패로 들어가거나, 짝이면 버림 더미로 갑니다.
- 뺏긴 쪽: 내 카드 하나가 ghost로 사라지며 "◯◯을 뺏겼어요"가 뜹니다.

❓ **Q23 - 손패 표시는?** (O3, O5)

➡️ 결정: 내 손패는 **서버 순서와 상관없이 랭크순으로 정렬해서 부채꼴로 겹쳐 보여 줍니다**(13장 넘어도 한 줄). 새로 들어온 카드는 "NEW" 표시와 빛으로 한 턴 동안 강조합니다. 조커는 항상 맨 오른쪽에 둡니다. 정렬은 내 화면에서만 이뤄지므로 상대에게 정보가 새지 않습니다.

❓ **Q24 - 서버가 손패를 섞는 동작은?**

➡️ 결정: **유지합니다.** 내 화면은 정렬해서 보여 주니 섞여도 보이지 않고, 상대는 슬롯 별칭만 보니 위치 정보가 의미가 없습니다. 바꿀 이유가 없습니다.

❓ **Q25 - 심리전 요소(표정 연기)를 넣을까요?**

➡️ 결정: 예. **공용 리액션** `game:reaction`을 만들어 이모지 6종(😏 😅 😱 🤞 😭 😎)을 말풍선으로 보냅니다. 서버는 허용 목록만 중계하고 1.5초 쿨다운을 둡니다. 도둑잡기에서 먼저 쓰고(조커를 앞에 두고 능청 떨기), 다른 게임에서도 같은 부품으로 켤 수 있게 둡니다. 원카드의 기존 리액션과는 분리해 두고 건드리지 않습니다.

❓ **Q26 - 카드 분배(27/26장)와 시작 턴은?**

➡️ 결정: 규칙 그대로 둡니다(전통 규칙이고, 시작 턴이 무작위라 평균은 같음). 화면에서 장수를 잘 보여 주는 것으로 충분합니다.

❓ **Q27 - 한 화면에 다 들어오게 하려면?** (O5, O6)

➡️ 결정: 세로 한 화면에 이 순서로 배치합니다.
- 상단: 상대 아바타 + 뒷면 부채꼴
- 중앙: 버린 짝 더미("14쌍") + 뽑기 연출 + 최근 한 줄 기록
- 하단: 내 손패 부채꼴
- 맨 아래: 리액션 줄

스크롤이 없습니다. 로그는 최근 3줄만 보여 줍니다("test가 ♥7을 뽑았어요 · 짝!").

## Round 5 — 제로

❓ **Q28 - 규칙을 바꿔도 되나요?** (§4)

➡️ 결정: 예. 사용자가 이유를 적지 않았지만 시뮬레이션이 분명합니다. 지금은 한 라운드에 결판 날 확률이 17~28%라 한 판이 15~25라운드입니다. 규칙의 **뼈대**(내 숫자 + 합계 예측을 동시에 공개)는 그대로 두고 아래 둘만 바꿉니다.

❓ **Q29 - 어떻게 바꿀까요?**

➡️ 결정:
1. **예측 가능 범위 = (내 숫자) ~ (내 숫자 + 5)**. 내가 낸 수보다 작은 합계는 불가능하므로 고를 수 없게 합니다. 선택지는 최대 6개의 칩이고, "8번 누르기"가 없어집니다.
2. **5라운드 점수 합산**으로 바꿉니다.
   - 합계를 **정확히 맞히면 2점**(둘 다 맞히면 각 2점).
   - 둘 다 못 맞히면 **합계에 더 가까운 쪽이 1점**(같은 거리면 0점).
   - 5라운드 뒤 동점이면 한 라운드씩 **서든데스**.

- 시뮬레이션(각 2만~4만 회): 라운드에서 점수가 갈릴 확률 **72~80%**(지금 17~28%), 5라운드 뒤 동점은 13~14%(서든데스 1~2라운드로 해결).
- 한 판은 **약 5~7라운드**로 줄어듭니다(지금 15~25).

대안으로 "정확 적중만 득점 + 범위 제한"을 검토했지만 결판 확률이 27%에 그쳐 폐기했습니다(끝 목록 D2에서 사용자가 현행 유지를 고를 수 있습니다).

❓ **Q30 - 조작은?** (§4)

➡️ 결정: 두 단계는 유지하되 훨씬 쉽게 만듭니다.
- 1단계: 큰 손 카드 6장(주먹~보)에서 내 숫자 선택.
- 2단계: **가능한 합계 칩**에서 예측 선택.
- 큰 "제출!" 버튼.
- 선택한 손은 크게 커집니다.
- 제출하면 내가 고른 값을 요약해 보여 줍니다("내 손 3 · 예측 5").

❓ **Q31 - 결과를 어떻게 설명할까요?** (§4)

➡️ 결정: "하나~둘~셋!"에 맞춰 두 손이 화면 가운데로 올라오고 **"3 + 2 = 5"** 를 계산해 보여 준 뒤 판정을 한 줄로 말합니다. 예를 들어 "test2 정확히 적중! +2", "둘 다 빗나갔어요 · test가 1 차이로 더 가까워요 +1", "둘 다 같은 거리 · 이번엔 무득점". 점수판은 5개 칸이 채워지는 진행 막대입니다.

❓ **Q32 - 코드는 어디에 둘까요?**

➡️ 결정: 제로를 `rps_screen.dart`(2,049줄)에서 떼어 **`zero_screen.dart`로 분리**합니다. 가위바위보 화면에서는 제로 코드를 지웁니다. 서버는 `game:rps:*` 이벤트와 `mode: 'hanabagi'`를 유지하고 득점 함수만 새로 추가합니다(영향 범위를 줄이려고). 새 규칙 필드는 `round_result`에 더합니다.

## Round 6 — 해적 룰렛

❓ **Q33 - 공정성과 방장 문제는?** (§5)

➡️ 결정:
- **선공은 서버가 무작위**로 정합니다(지금은 항상 첫 번째 플레이어).
- 구멍 수는 **짝수만**: 6 / 8 / 10 / 12(기본 8). 홀수의 선공 불리(54~60%)를 없앱니다.
- "방장만 시작·재시작" 제약을 없앱니다. 누구든 시작을 누를 수 있고, 재시작은 재시작 프로토콜로 합의합니다(Q8).

❓ **Q34 - 벌칙은?** (§5)

➡️ 결정: 폭발 뒤 **이긴 사람이 벌칙을 정합니다.**
- 프리셋 칩 10개: "어깨 주물러 주기", "칭찬 3가지", "노래 한 소절", "오늘 설거지", "딱밤 한 대", "사진 한 장 찍어 주기", "소원 하나 들어주기", "애교 한 번", "아이스크림 사기", "10분 안마".
- 직접 입력(최대 30자).

서버가 길이·공백을 검증해 졌던 사람에게 중계하고, 화면에 **큰 벌칙 카드**로 보여 줍니다. 진 사람이 "했어요!"를 누르면 이긴 사람에게 알림이 갑니다. 지금은 설명이 "벌칙 게임"인데 벌칙이 없다는 게 투박함의 핵심입니다.

❓ **Q35 - 연출은?** (§5)

➡️ 결정: 통 하나를 화면 중앙에 크게 두고 **구멍을 통 몸통 위에** 둡니다(원기둥 앞면에 가로 2~3줄). 칼 꽂기는 이렇게 연출합니다.
- 칼이 위에서 떨어져 구멍에 꽂히는 0.35초 애니메이션 + "슥" 소리.
- 통이 살짝 흔들립니다.
- 폭발할 때: 통 뚜껑이 열리며 해적이 하늘로 날아가고(별·파편 만화풍) "펑!" 소리.

별도의 숫자 격자는 없앱니다(구멍에 번호만 작게 표시).

❓ **Q36 - 긴장감은?** (§5)

➡️ 결정: 남은 구멍 기준 **폭탄 확률(%)**을 항상 보여 주고, 해적 표정이 확률 구간별 4단계(여유 → 걱정 → 땀 → 비명)로 바뀝니다. 확률이 30%를 넘으면 통이 떨리고 배경 음이 낮아집니다.

## Round 7 — 패널티킥

❓ **Q37 - 규칙은?** (§6)

➡️ 결정: **3방향(왼쪽·가운데·오른쪽)** 으로 바꿉니다. 키커와 키퍼가 동시에 고르고, 같으면 선방입니다. 높이는 없앱니다.
- 시뮬레이션(각 8천 판): 선방률 **33%**(지금 11%), 최종 무승부 **1.3%**(지금 14.8%), 조기 종료 49%.
- "6칸"(선방 17%, 무승부 6.8%)도 검토했으나 키퍼의 판단 거리가 부족해 폐기했습니다(끝 목록 D3).

❓ **Q38 - 읽을 거리를 어떻게 줄까요?**

➡️ 결정: 화면 위쪽에 **상대의 지난 킥(최근 5번) 방향 기록**을 점으로 항상 보여 줍니다("상대는 오른쪽을 자주 찼어요"). 키퍼는 습관을 읽고, 키커는 읽히지 않으려 합니다. 규칙은 그대로인데 판단할 근거가 생깁니다.

❓ **Q39 - 선공은?**

➡️ 결정: 첫 킥커를 **서버가 무작위**로 정합니다(지금은 항상 첫 번째 플레이어). 이후는 교대입니다.

❓ **Q40 - 인물을 어떻게 바꿀까요?** ("여성도 쉽게")

➡️ 결정: 작은 남성 축구 선수를 없애고 **귀여운 마스코트**로 바꿉니다. 둥근 몸에 팀 컬러 유니폼을 입고, **얼굴은 각자의 프로필 이모지**입니다(서버가 이미 `profileEmojis`를 줍니다). 색은 나=민트, 상대=분홍. 경기장은 맑은 낮, 밝은 잔디, 하늘 배경의 파스텔 톤입니다. 거칠거나 "게이머스러운" 요소(어두운 화면, 날카로운 서체)를 쓰지 않습니다.

❓ **Q41 - 쉽게 하려면 조작은?**

➡️ 결정:
- **한 번 탭 = 선택 + 바로 확정 대기**. 골대 위 3개 영역과 아래 큰 버튼 3개(왼쪽/가운데/오른쪽) 중 어느 쪽을 눌러도 됩니다.
- "슛!/막기!" 확정은 큰 단일 버튼입니다(지금은 칸 탭 후 작은 버튼).
- 설명은 첫 판 시작 전 **한 화면 요약**으로 보여 주고(기억해서 한 번만), 이후에는 상단 `?`로 다시 볼 수 있습니다. 요약 문구: "골대 세 칸 중 하나를 골라요. 키퍼가 같은 쪽을 고르면 막혀요!"

❓ **Q42 - 시간 제한은?**

➡️ 결정: 20초. 시간이 지나면 **무작위로 자동 선택**합니다(연속 3회면 기권, 기존 AFK 안전망 유지). 화면에 부드러운 시간 링이 돕니다.

❓ **Q43 - 연출은?**

➡️ 결정: 지금 2.4초 연출을 **0.9초 비행 + 키퍼 다이브 + 그물 출렁 + 관중 반응**으로 다시 짭니다. 골은 색종이와 환호, 선방은 "나이스!"와 아쉬운 탄식입니다. 소리: 휘슬, 킥, 그물, 환호, 탄식. 연출 중에도 건너뛰기(탭)를 허용합니다.

❓ **Q44 - 진행 중인 옛 판과 호환은?**

➡️ 결정: 선택 값이 `0~8`에서 `0~2`로 바뀝니다. 웹만 운영하고 서버와 웹을 함께 배포하므로 **호환 코드를 두지 않고**, 복원 시 옛 형식(선택 범위 밖)을 감지하면 그 판을 정리합니다(TTL이 최대 1시간).

## Round 8 — 순서와 위험

❓ **Q45 - 어떤 순서로 만들까요?**

➡️ 결정:
1. **공통 기반**(F01~F05): 카드 그림, 효과음 공용화, 재대결 합의·gameId, 잠수 안내, 공용 연출 부품.
2. **블랙잭**(규칙 변경이 가장 크고 카드 그림을 먼저 검증).
3. **도둑잡기**(같은 카드 그림 재사용).
4. **패널티킥** → 5. **해적 룰렛** → 6. **제로**.
7. **최종 검증**(두 계정 실플레이, 문서 갱신).

게임마다 서버(엔진·소켓·테스트) → 클라이언트(화면·테스트) 순으로 세로 조각을 만듭니다.

❓ **Q46 - PR은 어떻게 나눌까요?**

➡️ 결정: **공통 기반 1개 + 게임별 1개씩**(총 6개). `main` 머지는 프로덕션 자동 배포이므로 각 PR은 **사용자 확인 뒤에** 머지합니다. 서버와 웹이 함께 바뀌는 PR은 같은 PR 안에서 함께 배포됩니다.

❓ **Q47 - 테스트 전략은?**

➡️ 결정:
- **엔진은 TDD**: 규칙 테스트 + **균형 테스트**(시뮬레이션으로 무승부율·결판 확률·선방률이 목표 범위인지 확인, 예: 블랙잭 최종 무승부 < 3%, 제로 라운드 결판 > 65%, 패널티킥 선방률 30~36%).
- **소켓 회귀**: 새 이벤트와 재시작·복원·AFK.
- **Flutter**: 위젯 테스트 + 로컬에서 만드는 스크린샷(`TANK_SHOTS`와 같은 환경변수 방식).
- **실플레이**: 두 계정으로 각 게임 한 판 이상.

골든 이미지는 CI 렌더러와 달라 비교용으로 커밋하지 않습니다(윷 보드 골든 문제와 같은 이유).

❓ **Q48 - 이번에 하지 않을 것은?**

➡️ 결정: 아래는 범위 밖입니다.
- 새 게임 추가, 다른 10종의 개편
- 오디오 파일·이미지 에셋 도입
- 코인 상점·아이템과의 연동 변경
- 블랙잭 더블다운/스플릿, 딜러 모드
- 도둑잡기 손패 드래그 정렬(심리전의 다른 형태)
- 모바일 앱 전용 기능(진동 등)
- `socket.js`/`SocketService` 구조 분리
