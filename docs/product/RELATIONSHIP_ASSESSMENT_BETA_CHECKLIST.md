# 관계이해 beta smoke checklist

이 문서는 관계이해 기능의 구현 완료 후 사용자가 직접 수행하는 점검 절차다. 배포나 운영 데이터 변경을 수행하지 않으며, 테스트 계정 또는 별도로 만든 두 계정으로 실행한다.

## 자동 검증

서버:

```bash
cd services/realtime-server
npm run check
node --test test/relationship-explanation-provider.test.js
npm test
```

`TEST_DATABASE_ADMIN_URL`과 `TEST_REDIS_URL`이 없으면 DB·Redis 통합 테스트는 skip된다. 이 상태에서는 통합 흐름이 검증된 것으로 간주하지 않는다.

Flutter:

```bash
cd apps/secret_base_app
flutter analyze
flutter test
```

## 수동 2인 흐름

1. 두 계정으로 로그인한다. 제공된 테스트 계정은 `test@test.com / test`, `test2@test2.com / test2`다.
2. 홈의 관계이해 진입 카드에서 관계이해 화면을 연다. 하단 탭이 추가되지 않았는지 확인한다.
3. 각 계정에서 출생 프로필을 저장한다. 양력/음력, 날짜, 시간대는 입력하고 출생 시각과 출생지는 비워 저장해본다.
4. 개인검사를 시작하고 문항 하나를 선택한 뒤 앱 화면을 나갔다가 다시 들어온다. 진행률과 저장된 답변이 복원되는지 확인한다.
5. 개인검사를 완료하면 차원별 점수와 전체 경향이 즉시 보이는지 확인한다. 결과에는 비임상적 참고 정보라는 안내가 있어야 한다.
6. 개인 결과에서 `설명 요청하기`를 누르기 전에는 설명 생성 요청이 없어야 한다. 버튼을 누른 뒤에는 provider가 비활성인 기본 설정에서 고정 설명과 fallback 안내가 보여야 한다. 핵심 점수는 요청 전후 동일해야 한다.
7. 두 계정에서 같은 커플검사를 진행한다. 한 명만 완료했을 때는 대기 상태를 확인하고, 두 명이 같은 버전을 완료한 뒤에만 공유 결과가 열리는지 확인한다.
8. 궁합 dashboard에서 준비된 카드와 대기 중인 카드가 독립적으로 표시되는지 확인한다. 궁합 상세의 설명도 사용자가 요청한 뒤에만 생성된다.
9. 한 계정에서 연결을 해제한다. 커플검사·궁합·궁합 설명은 접근할 수 없어야 하고, 개인검사 history는 계속 열려야 한다.
10. 같은 두 계정으로 다시 연결한다. 기존 Couple이 복원되고, 이전 커플 결과가 다시 같은 관계 범위에서 보이는지 확인한다.
11. 가능하면 세 번째 계정과 새로 연결한다. 새 커플에서는 이전 커플의 커플검사·궁합 결과가 노출되지 않고 새 대기 상태로 시작하는지 확인한다.

## Known limitations

- 현재 검사는 자기이해와 관계 대화를 위한 비임상적 도구다. 병원 검사, 의료 진단, 치료, 위기 대응을 대체하지 않는다.
- 사주 계산·오늘의 운세 생성·상담 채팅은 아직 포함하지 않는다. 출생 정보는 후속 기능을 위해 저장만 한다.
- LLM은 기본적으로 비활성화되어 있으며, 무료 provider adapter가 설정되지 않아도 결정론적 결과와 고정 설명이 동작해야 한다. 스트리밍과 백그라운드 생성은 포함하지 않는다.
- 프라이빗 상담 원문과 운영자 감사 로그는 이번 범위가 아니다. 향후 상담 기능을 추가할 때 별도 보안 설계가 필요하다.
- 후보 문항 pool은 버전 관리되지만 현재 active 문항 선택과 점수 규칙은 제품 초기 고정값이다. 임상적 타당도나 심리측정학적 완전성을 주장하지 않는다.
- 운영 배포는 이 체크리스트와 사용자의 실제 수동 테스트 승인 이후 별도 작업으로 진행한다.
