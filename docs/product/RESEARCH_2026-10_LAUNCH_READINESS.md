1. **푸시 알림이 전혀 없다.** 앱(firebase 계열 의존성 없음)과 서버(전송 코드·토큰 테이블·스케줄러 없음) 모두 미구현이다. 커플 앱의 리텐션 루프(오늘의 루프 공개, 상대 기록 알림)가 알림에 의존하므로 출시 P0다. [코드]

## 2. 알림 시스템

### 2.1 클라이언트

- **통합 스택: Firebase Cloud Messaging(FCM)**. Flutter는 `firebase_core` + `firebase_messaging`을 쓰고 `flutterfire configure`로 설정한다. Apple 플랫폼에서는 FCM API 호출 전에 APNs 토큰이 준비됐는지 확인(`getAPNSToken()`)해야 한다. 웹은 `getToken()`에 VAPID 키를 넘긴다. [1차: [Firebase Flutter 클라이언트 가이드](https://firebase.google.com/docs/cloud-messaging/flutter/client)]
- **iOS**: Xcode에서 Push Notifications와 Background Modes(Remote notifications)를 켜고, Apple 개발자 센터에서 APNs 인증키(.p8)를 만들어 Firebase 콘솔의 Cloud Messaging 탭에 키 ID·팀 ID와 함께 올린다. 인증키는 만료되지 않지만 인증서는 매년 만료된다는 2차 설명이 있다. [1차 + 2차]
- **Android 13(API 33)+**: `POST_NOTIFICATIONS` 런타임 권한을 매니페스트에 선언하고 요청해야 한다. 거부하면 알림 서랍에 표시되지 않는다. API 33 이상을 타깃으로 하면 권한을 요청할 **시점을 앱이 고를 수 있다**(권장). 알림 채널(채널별 중요도·소리)은 공식 문서의 채널 절을 별도로 확인해야 한다(이번 검색에서는 2차 자료만 확인). [1차: [Notification runtime permission](https://developer.android.com/develop/ui/views/notifications/notification-permission)]
- **권한 요청 UX 제안(해석)**: 첫 실행 즉시 요청하지 않고, 커플 연결 완료 직후나 첫 기록 후처럼 "상대가 남기면 알려드릴까요?" 문맥에서 요청한다. 거부 사용자는 설정 이동 안내를 한 번만 보여준다.
- **포그라운드 표시**: FCM은 앱이 켜져 있을 때 시스템 알림을 자동으로 띄우지 않으므로 `flutter_local_notifications`로 인앱 배너/로컬 알림을 보조한다(해석, 구현 단계에서 검증).

### 2.2 웹 푸시

- 이 서비스의 현재 운영 형태가 Flutter 웹(`secretbase.cloud`)이므로 웹 푸시도 필요하다. 서비스 워커 등록·VAPID 키·알림 권한이 필요하다.
- **iOS Safari 제약**: iOS 16.4 이상이며 **사이트를 홈 화면에 추가한 웹앱**에서만 푸시가 가능하고, 권한 요청은 **구독 버튼 같은 직접 사용자 동작** 안에서 해야 한다. 한 벤더 가이드는 거부 후 재요청을 하려면 홈 화면 추가를 지우고 다시 해야 한다고 주장한다(미확인). 일부 개발자는 푸시가 간헐적으로 멈춘다고 보고한다. [2차: [OneSignal](https://documentation.onesignal.com/docs/en/web-push-for-ios), [Braze](https://braze.com/docs/developer_guide/platform_integration_guides/web/push_notifications/safari_mobile_push), [Notificare](https://notificare.com/blog/2023/03/27/web-push-in-ios-safari/)]  → WebKit 공식 발표문 원문은 이번 조사에서 열지 못했으니 구현 전 직접 확인한다.
- 이 앱은 현재 `index.html`에서 서비스 워커를 **모두 해제하고 캐시를 삭제**하는 스크립트를 실행한다(배포 캐시 문제 회피용). 웹 푸시용 서비스 워커를 쓰려면 이 정책과 충돌하므로 **푸시 전용 워커를 별도 스코프로 분리**하는 설계 결정이 필요하다. [코드]

### 2.3 서버

- 발송: `firebase-admin`(FCM HTTP v1)으로 Android·iOS·Web을 하나의 경로로 보낸다. 대안은 웹만 `web-push`(VAPID) 직접 발송이다. 이 앱은 Node/Express이므로 `firebase-admin`이 가장 적은 코드로 통합한다(해석).
- **토큰 저장(제안 스키마)**: `device_tokens(id, user_id, platform[android|ios|web], token UNIQUE, app_version, last_seen_at, revoked_at)`. 로그아웃·삭제·FCM 무효 응답 시 폐기. 한 사용자 여러 기기를 허용한다.
- **대상 선정**: 항상 인증된 `user_id → 활성 Couple → 상대 user_id`에서 도출한다(기존 "Couple 안에서만 합쳐진다" 원칙 유지). 알림 본문에는 정확한 장소·민감 내용을 넣지 않는다(리텐션 리서치 원칙).
- **설정 모델(제안)**: `notification_prefs(user_id, partner_moment, today_loop, anniversary, game_invite, marketing, marketing_night, quiet_start, quiet_end)`. 서비스성은 기본 ON·종류별 OFF 가능, 마케팅은 기본 OFF.
- **스케줄러 필요**: "오늘의 루프" 공개 시각, 기념일 D-day, 미완료 리마인더는 서버 시간 트리거가 필요한데 현재 스케줄러가 없다. 단일 서버(PM2 fork)이므로 `node-cron` 또는 DB 기반 잡 테이블로 시작하고, 중복 실행 방지(Redis 락)를 둔다(해석).

### 2.4 한국 규제 (광고성 vs 서비스성)

- 광고성 정보는 사전 명시 동의가 필요하고, **오후 9시~다음 날 오전 8시 광고성 정보 전송은 별도 동의**가 필요하다. OS 알림 권한 허용은 광고 수신 동의와 별개다. 광고는 광고 표시·전송자 명칭·수신 거부 방법을 포함하고, 수신 거부에 로그인을 요구하면 안 된다. 동의는 2년마다 재확인 대상이라는 해설이 있다. 정보성 메시지에 광고 문구·링크가 섞이면 광고로 판단될 수 있다. [2차: [푸시 운영 가이드](https://www.digitalmarketer.co.kr/class/app-marketing-campaigns/push-notification-operations), [Solapi 정책](https://solapi.com/guides/policyguidelines)]
- **중요**: 이번 검색은 법조문 원문(정보통신망법 제50조)을 열지 못했고 실무 해설만 확인했다. **적용 전 국가법령정보센터 원문과 시행령을 직접 확인하고 필요하면 전문가 검토**를 받는다.
- 설계 원칙(해석): 이 서비스의 핵심 알림(상대 기록, 오늘의 루프, 기념일)은 이용자가 요청한 서비스 기능의 일부이므로 **서비스성으로 분류하고 광고 문구를 절대 섞지 않는다**. 마케팅 푸시는 첫 출시 범위에서 **아예 만들지 않는 것**이 가장 안전하다.

### 3.2 Apple App Store

- **계정 삭제(5.1.1(v))**: 계정 생성을 지원하면 **앱 안에서 삭제를 시작**할 수 있어야 한다. 이메일·전화 같은 지원 채널만 요구하는 방식은 규제 산업이 아니면 불가이고, 확인 단계 추가(이메일 코드 등)는 허용되나 불필요하게 어렵게 만들면 반려된다. [1차: [Apple 계정 삭제 안내](https://developer.apple.com/support/offering-account-deletion-in-your-app)]
- **UGC(1.2)**: 약관 동의, 부적절 콘텐츠 필터, 신고, 차단, 24시간 내 조치가 요구된다고 반려 통지문에서 인용된다. 가이드라인 원문은 이번 조사에서 확인하지 못했다. 이 앱은 커플 1:1 비공개라 공개 UGC와 성격이 다르나 **심사에서 어떻게 해석할지는 불확실**하다(결정 필요). [2차: [Apple Forums 1.2](https://developer.apple.com/forums/thread/807358)]
- **필수 선행**: iOS 프로젝트 생성, Apple Developer Program 가입, Bundle ID, APNs 키, TestFlight, 앱 개인정보 라벨, 개인정보 처리방침 URL. 현재 저장소에 `ios/`가 없다. [코드]
- Google 로그인을 쓰면서 다른 소셜 로그인도 제공하는 경우의 "Sign in with Apple" 요구 여부는 이번에 조사하지 않았다(구현 전 확인).

## 6. 오너가 결정해야 할 것

1. **첫 출시 채널 범위**: 웹 + Android 비공개 테스트까지만인가, iOS 동시 출시인가? (iOS는 프로젝트 생성부터 필요)

3. **알림 범위**: 서비스성 알림만 출시하고 마케팅 푸시는 보류하는 안에 동의하는가?
4. **알림 시간 정책**: 방해금지 기본값(예: 22:00~08:00)과 "오늘의 루프 공개 시각"을 고정할지, 커플별로 정할지?
5. **웹 푸시 우선순위**: 웹 사용자가 베타의 주 경로라면 웹 푸시를 P0로 올릴지, 앱 푸시 먼저인지?
6. **신고·차단 필요 여부**: 커플 1:1 비공개를 이유로 생략할지, 심사 위험을 줄이려 최소 신고 기능을 둘지?
7. **스테이징 분리 시점**: 지금(P0)인가, 베타 확대 직전인가? (현재 테스트 도메인이 운영 DB를 공유)
8. **정식 서명 키 관리**: 키스토어 보관 위치와 백업 책임자를 정할 것(분실 시 업데이트 불가)
